# BLU 整段 GCD 入口排除的实测依据

2026-10-30：**按用户决定保留 BLU 的整段 GCD 入口排除，并在 `canSearchSpeedInterval` 附近注明实测。** 当前实现已出现明显性能退化，不能像固定速度相关上界那一项一样，按“性能接近、统一策略”直接移除。这里记录的是性能理由，不是数学上不能使用整段搜索。

## 测试改了什么

冻结当时工作区两份代码（已经包含固定速度相关线性上界的统一改动），open 仅移除 `canSearchSpeedInterval` 中的 `input.damage.job !== 'BLU'`。两版添加相同的固定速度／整段查询计数。搜索规模阈值、候选范围、评分、预热、分片、共享与重启规则不变。

青魔的特殊伤害公式仍保留：固定输出模仿的暴击／直击加成，以及按装备智力查询的额外武器伤害。当前网站没有治疗／防护模仿选择，本轮没有声称覆盖这些模式。普通职业的副属性预算界和相关线性上界对 BLU 的公式保护也没有放开。

输入从当前页面捕获；4 核配额、4 Workers、auto、每分片最多 4 次重启，串行、新 Chromium、交替版本顺序。单次预算 60 秒，完成对照没有发生重启。每格仅一次，不能由此估计稳定方差，但两例的数倍退化和约百倍分支增长足以反对直接全局放开。

5 组、10 次运行全部完整结束，配对目标值一致；独立 Python 重建装备、镶嵌、食物和属性，核对 GCD、暴击条件及青魔伤害，全部通过。open 的整段查询计数均大于零，baseline 均为零，实际触发了所测开关。

不能把这些数据概括为“青魔每例都慢”：50／60 级与 70 级低暴击确实更快。当前保留的是防止已实测重大回退的保守默认，不是已经证明固定速度在所有 BLU 输入上都更优，也没有新增按等级／暴击模式的白名单。

## 为什么 375 会明显退化

不限暴击例：

- 已完成查询的搜索分支数：6,406,991 → 646,477,296，约 **101 倍**。
- 累计 Worker 搜索时间：2,171 ms → 124,370 ms。这里是并行 Worker 计时之和，不是用户等待时间。
- 分片：16 → 4；整段路线减少了重复准备工作，却没能抵消搜索增长。

固定速度路线先物化部分属性组合，用去重和支配筛选压缩状态，再转树搜索。整段路线提前进入树搜索，省去这段属性状态 DP。对普通职业，副属性总预算和相关线性上界能补偿一部分松弛；当前 BLU 因特殊公式不使用这两层界，只剩较松的独立属性上界等检查。因此，省下的预处理可能被大量额外分支抵消。这是代码结构与计数一致的解释，未把各子组件逐个消融后的收益冒充本轮实测。

## 正确性与覆盖边界

- 两个冻结版本都通过现有 8 个 optimizer 测试文件及生产构建。
- open 新增 1,200 组青魔原生 GCD 区间独立穷举对照，使用真实智力换算表与 50／60／70／80 级参数，全部通过。
- 小规模整条流程对照增加 12 个青魔种子，各检查高／低／不限暴击（包括无解情况），与 JS 结果比较，并断言青魔实际进入整段后端，全部通过。
- 本轮真实输入的智力换算表单调，长度 1,308；四个同步输入的独立最大装备智力分别为 333／568／893／1,285，落在表内，食物不增加智力。由此支持这些输入的独立属性上界，但不声称完成浮点实现的形式化证明。
- 80 级／同步 525／不限暴击的 open 在 60 秒达到预算，0/4 分片完成；只能确认当前候选可行，不能确认最优或完整耗时。baseline 尚未完成时，用户决定保留排除并要求注明，遂终止余下矩阵。该例没有完整配对，**不用于计算性能倍率**。
- 非 2.50 GCD 与较窄范围的真实输入已经准备，但尚未执行；不能把准备了输入写成测过。后续若重评估，应补这些覆盖及重复计时。

当前修改只有代码注释和记录，运行中的 BLU 排除保持原状。重新评估的前提是补齐适用于 BLU 的强上界或改善整段搜索结构，再复测回退案例；不能直接套用普通职业的公式来抹平差异。
