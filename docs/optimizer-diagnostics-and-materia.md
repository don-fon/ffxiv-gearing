# 自动配装诊断与魔晶石算法分析（2026-10-26）

## 在浏览器中确认引擎

访问预览页，打开开发者工具 Console，筛选 `[自动配装]`，再开始计算。生产构建保留这些 `console.log`，版本标记为 `2026-10-26-console-v1`。页面会转发 Worker 的诊断摘要，方便在页面上下文查看。

- `输入概况`：页面路径、职业、品级筛选、同步品级、Worker 数、原始候选数、范围外同步候选数，以及几件范围外衣服实际参与求解的同步属性。
- `WASM 下载完成`：下载 URL 和字节数。
- `引擎就绪`：`engine: "WASM"` 或 `"JavaScript"`；初始化失败会用 `console.warn` 打印具体原因和回退动作。
- `计算中`：有搜索/筛选回调时约每 5 秒打印一次，避免逐分支刷屏。
- `规划完成`、`分片完成`：记录阶段/分片耗时及原生调用计数。
- `全部完成`：从加载数据开始的总耗时、完成分片数、结果评分和最终装备的原始品级/同步标记。

`engine` 表示可用后端；`wasmUsed`、`wasmSearchCalls`、`wasmParetoCalls` 表示是否实际进入原生热点。全部锁定等简单问题可能在调用内核之前就已完成，此时加载成功但调用数为零是合理的。

诊断字段含义：

| 字段 | 含义 |
| --- | --- |
| `wasmSearchMs` | 原生搜索适配器耗时，包含打包及回调 |
| `wasmParetoMs` | 原生属性支配筛选适配器耗时，包含打包 |
| `otherMs` | 完成时的剩余耗时，包括 JS 状态展开、建树等 |
| `wasmVisitedBranches` | 累计原生属性树分支，含有界预搜索 |
| `wasmEvaluatedCombinations` | 原生实际检查的完整属性组合 |
| `jsTreeFallbacks` | 原生适配器未承接、交回 JS 的树搜索次数 |
| `wasmMemoryMiB` | 当前 WASM 线性内存高水位；不包含 JS 对象，不能当作 Worker 总内存 |

这些都是每个 Worker 任务的墙钟时间。并行任务的耗时不能直接相加当作用户等待时间；支配筛选计数也是累计处理量，可能多次处理同一候选。

## 为什么筛选 350–375 仍选出 500 衣服

这部分是先前的候选范围错误，已按用户要求修正。此前通过“同步后双副属性封顶”等规则引入范围外装备，不符合筛选语义。

现在候选来源直接复用页面 `store.filteredIds`，不再另算同步候选范围：

- 品级范围内、列表显示的装备参与比较。
- 用户手动选定、被列表保留显示的装备可以作为范围外例外参与比较。
- 仅加载过或仅满足同步属性上限的范围外装备不会加入。
- 手动选定不等于锁定，勾选锁定后才固定装备；显式排除、自定义属性未填写等求解约束仍生效。

原始输入中的 956 件候选、909 件范围外同步装备，以及下文的旧性能数据属于修正前输入，不能用来描述修正后 350–375 的候选或耗时。详情见 [候选范围修正](optimizer-candidate-scope.md)。

## 完整战士场景：确实使用 WASM，仍为分钟级

生产 Chromium、4 Worker、350–375 筛选、同步 375、GCD 2.50、最低坚韧 0%、无锁定、全部食物：完整求解 **166.613 秒**，16/16 分片完成，伤害期望 `8.080836870815013`，与参考精确解一致。

16 个搜索分片全部使用 WASM，累计：

- 原生搜索调用 208 次；另有规划阶段 48 次有界搜索。
- 原生支配筛选调用 1120 次。
- 检查约 31.85 亿个原生属性树分支、4243 万个原生完整属性组合。
- 每任务计时汇总：搜索适配器 545.749 秒、支配筛选适配器 15.812 秒、其他 61.881 秒。搜索约占该汇总的 87.5%；这些并行耗时不等于整次等待时间。

原始数据：[完整诊断](benchmarks/warrior-full-diagnostics.json)。本次耗时与此前 158.6 / 174.4 秒的记录同量级，不能据单次比较宣称日志带来提速。用户电脑是否使用 WASM，仍需看其本机日志；云端这次使用了 WASM，不代表本机没有加载失败或使用旧页面。

## 魔晶石算法还有哪些空间

### 已有优化：逐孔合并相同属性结果

`gearOptions` 每处理一个孔就按最终属性签名去重，并非把所有孔位排列一直保留到最后。五个同值孔、五种属性，朴素排列有 5⁵ = 3125 个；忽略溢出时只有 C(9,4) = 126 种属性计数组合，当前算法已经在逐孔过程中合并排列重复。属性溢出还会继续合并。

因此，“改成枚举各属性镶嵌数量”主要能减少中间对象分配，不能再把当前 126 个结果误算成 3125 个。不同数值/品级的孔、每件装备属性上限、锁定镶嵌都必须保留。

### 已测原型：提前排除不可能满足目标 GCD 的速度镶嵌

原型只在各装备速度属性非负时启用，用目标 GCD 和食物计算保守速度上界；某件装备或中间镶嵌已超出上界时，不继续生成。它只在分析进程内修改源码副本，**没有合入生产求解器**。

固定食物 49240，锁定参考方案的武器/手套/鞋及镶嵌，速度贡献 0，同一输入、新 Node 进程串行测试：

| 项目 | 当前算法 | 提前速度筛选原型 |
| --- | --- | --- |
| 生成的镶嵌选项 | 4163 | 1532 |
| 镶嵌生成耗时（两次） | 29.75 / 29.32 ms | 13.19 / 11.56 ms |
| 完整求解耗时（两次） | 6.187 / 5.862 s | 6.493 / 5.675 s |
| 最优伤害 | 8.080836870815013 | 相同 |

未锁定、只规划的单次对照：总耗时 619.8→584.6 ms，镶嵌生成 36.2→9.8 ms。生成阶段确实省了约六成选项，但完整求解没有稳定提速，更没有达到此前要求的 50% 提升，因此不采用该原型。原型只验证了这组输入，不据此宣称其已完成通用正确性验证。

原始数据：[局部原型对照](benchmarks/materia-early-speed.json)。复现：

```sh
node scripts/analyze-optimizer-materia.mjs baseline
node scripts/analyze-optimizer-materia.mjs early-speed
node scripts/analyze-optimizer-materia.mjs baseline --unlocked --plan
node scripts/analyze-optimizer-materia.mjs early-speed --unlocked --plan
```

### 值得优先验证的方向

1. **收紧剩余伤害上界**：目前主要时间消耗在证明其他分支不可能更优。进一步利用同一节点内暴击、信念、直击、坚韧总预算及属性区间关联，争取更早剪枝；必须保留取整和食物封顶下的保守性，并用穷举 oracle 验证。
2. **改进拆树策略**：当前主要按候选数量选择待拆节点。可以测试按“拆分后能降低多少伤害上界／能排除多少工作量”选择节点。多算上界也有成本，需要用完整同输入计时决定是否采用。
3. **缓存或统一分发准备结果**：食物/候选分片会重复生成一部分相同选项。需要同时衡量 JS 对象、消息传输及多 Worker 内存成本；完整场景中这部分比例较小，预期优先级低于前两项。
4. **可选的快速结果展示**：规划阶段已有合法初始方案，可以另行设计“先查看当前最佳、继续证明最优”。这改善等待体验，不能把尚未证明的方案标成精确最优；本轮没有改变结果语义。

本轮加入的是诊断和规则说明，没有用未经验证的贪心镶嵌或近似结果替代精确搜索。

验证：71 项优化器测试、11 项生产浏览器测试、lint 和生产构建通过。浏览器测试覆盖诊断日志保留、三档偏好各自的 WASM 加载与回退，以及 Worker 诊断转发到页面 Console。
