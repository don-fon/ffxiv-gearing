# 固定速度路线的相关线性上界验证

日期：2026-10-30。**当前决定：按用户要求移除固定速度路线的额外排除，统一相关线性上界的启用策略。** 对照未发现结果不一致，也未显示显著加速；采用理由是减少没有明确必要性的历史例外。此前以“未达到 50% 改善”为由保留排除的判断已被此决定替代，原始测量不变。

这里的“性能基本持平”不是统计上证明完全等价：7 个受影响配置各三次均值仍有快 3.6% 至慢 8.8% 的差异，龙骑约慢 0.15 秒。这是接受小幅成本变化以简化策略，不是新的性能提升声明。

按用户安排，搜索规模阈值、BLU 排除另记为[后续 TODO](optimizer-current-algorithm.md#待验证-todo2026-10-30)，本轮保持不变。梯度实验继续归档，本轮验证的是已有的静态相关线性上界。

## 唯一算法变量

对照实验 baseline 的 C 内核启用条件包含（当前已删除中间的路径条件）：

```c
context[15] && (!context[56] || context[57]) && ...
```

- `context[15]`：副属性预算／上界公式的前提成立。
- `context[56]`：可确认 TEN 完全不参与评分的普通职业模型。
- `context[57]`：当前查询带整段 GCD 的速度区间约束。

baseline 保持路径限制；open 只移除 `(!context[56] || context[57])`。两版均保留 100 万组合阈值、正倍率、合法食物、参考因子等保护，也不改变整段 GCD 的 100 亿入口阈值、预热、分片、BLU 条件和调度。

给两版增加相同的实验计数器：查询总数、满足其他条件但被路径限制拦截的固定速度查询数、实际启用数、暴击段数、支持函数扫描点数。生产源码没有加入这些计数器。baseline 为记录资格，先检查其他条件再施加旧路径限制；通过同样的资格检查后，两版仅此路径开关不同。

“固定速度查询”和“整段查询”是单次后端调用的属性，不能简单按整个职业／输入分类。同一配置的不同食物、分片或预热可以走不同路线。龙骑 605／2.50 就包含 16 次满足新增路径条件的查询。

## 正确性依据和检查

在线性上界现有公式保护条件成立时，其推导不要求速度必须作为一个区间一起搜索：

1. 每个暴击段内，用暴击因子的割线给出上界，再对其对数和其余正因子的对数取切线。
2. 对每个实际候选组计算线性形式的最大值，保留组内属性之间的关系；将各组最大值相加，给出组合的乐观界。
3. 将某个候选组限制为固定速度的子集，不会破坏“最大值不小于其中任一候选”的性质；无 TEN 模型也已经明确省略 TEN 因子。
4. 暴击段覆盖、叶子精确评分以及速度路径本身的可达性约束仍然保留。

因此，没有发现必须因“无 TEN＋固定速度”关闭该上界的数学理由。这是基于现有公式假设的推导，不是浮点 C 实现的形式化证明。

验证包括：

- 两版均通过现有 8 个 optimizer 测试文件和生产构建；其中 WASM 文件有 14 项测试，包含既有 900 组速度区间穷举对照。
- 新增 **1,200 组固定速度后端的独立穷举对照**，覆盖 STR／DEX／INT／MND、物理／魔法武器、不同等级、食物封顶、分数属性、高／低／不限暴击和接近最优的初始下界。两版均通过。
- 其中 **1,028 组**满足上界公式前提：baseline 实际开启 0 次，open 开启 1,028 次，并处理 49,543 个暴击段。其余组仍由既有食物等保护关闭，不把它们算作新增路径覆盖。
- **20 个完整配置、68 次浏览器运行全部完成**；同配置目标值和暴击阈值一致。独立 Python 重建装备、魔晶石、食物、属性、GCD、减伤及评分，全部通过。完整案例一致用于查错，不能单独证明所有剪枝永远正确。

## 性能方法

冻结当前工作区的两份源码，保留源码／WASM／构建产物指纹。4 核配额、4 Workers、auto 引擎、默认候选共享和每分片最多 4 次重启；每次使用新的 Chromium，串行运行，交替版本顺序，不与编译或测试并发。每次预算 180 秒，本轮全部在预算内完成。

20 个配置先各跑两版一次，再对实际受影响的 7 个配置各追加两轮，两版各累计 3 次。受影响配置全部无重启。其余 13 个配置只作覆盖和回归对照，不把单次计时波动归因给没有触发的开关。

### 为什么分支减少很多，耗时却基本不变

画家 375／2.49 是最清楚的例子：

| 指标 | 原版 | 放开路径限制 |
| --- | ---: | ---: |
| 新路径上界查询数 | 0 | 420 |
| 已完成查询的搜索分支数 | 1,456,685 | 113,461 |
| 暴击段配置次数 | 49 | 4,999 |
| 支持函数扫描候选点次数 | 1,886,554 | 20,342,122 |
| 累计 Worker 搜索耗时，三次均值 | 953.0 ms | 1,079.7 ms |
| 整体耗时，三次均值 | 4.357 s | 4.277 s |

分支减少约 92.2%，但支持函数扫描增加约 10.8 倍。线性支持值按节点和当前暴击段缓存；下一次查询／暴击段更换权重后，不能直接复用旧值。多个固定速度查询反复配置段和扫描候选，抵消了减少分支的收益。扫描次数包含重复访问，不是新增独立装备组合数。

累计 Worker 搜索耗时是多个并行 Worker 的搜索计时之和，不能当作整体等待时间相减。本轮整体快约 1.8%，而搜索计时反而增加约 13.3%，所以不能声称这 1.8% 是上界带来的稳定加速；预处理、JIT、浏览器调度都有波动。

画家 375／2.50 的分支也从 56,233 降到 15,246，但原版累计搜索仅约 120 ms，整体约 2.21 秒；即使把这部分几乎消除，也不足以让整个任务快一倍。白魔高暴击的累计搜索均值从 98.3 ms 降到 78.7 ms，端到端仅约 2% 的变化，不能称为显著性能收益。

## 当前决定与边界

- 对照阶段未改生产源码，261 个 `src` 文件哈希与实验前一致；随后按用户要求应用路径简化，重新编译 WASM。固定速度和整段 GCD 查询统一使用已有公式保护和规模条件，没有新增按职业或案例的白名单。
- 将固定速度穷举回归扩充为 180 组坦克＋1,200 组无 TEN 输入，覆盖四种主属性、两种武器伤害轴、食物封顶、分数属性、暴击约束和接近最优的初始下界。实际源码与重建 WASM 已通过 `npm run test:optimizer`（8 个文件）、`npm run lint` 和 `npm run build`。
- 已有静态相关线性上界保留；梯度细化仍归档。搜索规模阈值和 BLU 排除保持 TODO。
- 本轮证据不支持“固定速度路径在数学上不能使用”，也不足以证明“所有固定速度输入关闭一定更快”。因此移除该历史路径排除；不能把此次决定概括为已证明所有固定速度输入开启都更快。
- 没有重跑骑士 605／2.45／最低减伤 10% 等坦克长例：目标条件只额外限制无 TEN 的固定速度查询，坦克不受该项排除影响。本轮另以战士无减伤／最低 10% 和武僧长例作回归；不把缺少这次复测的历史长例耗时标成新结果。
- 若后续重新评估，关键应是降低多查询、多暴击段的支持函数扫描成本，并测端到端收益；不能只用“分支数下降”代替性能采用标准。搜索规模阈值和 BLU 入口仍留在 TODO，本轮没有确定其优势区间。
