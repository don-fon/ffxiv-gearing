# 自动配装分流审计（2026-10-28）

范围：候选输入、JS求解器、WASM适配器、原生内核和Worker配置。此轮为审计，未修改生产求解逻辑。
检查代码条件、提交来源，并对青魔做内存中移除限制的正确性实验。下列优先级是后续验证顺序，不是已测得的性能排名。

## 需要处理或补证据的项目

### 1. 魔法武器遗漏主属性分裂启发式（已确认硬编码不对称）

`src/optimizerSearch.c:278` 的主属性不确定性只使用 `(n[6]-n[19])*plane_weights[6]`。
MDMG在索引7；魔法攻击的武器切线权重在索引7，索引6权重为0，因此魔法武器这一项实际上没有参与分裂优先级。
`src/optimizerWasm.ts:91` 打包的最小武器属性也固定读取PDMG，需要同时改为所选武器伤害轴，不能只改C下标。
这是物理/魔法之间真实的实现遗漏，不是职业机制所需。影响搜索顺序，未发现因此漏解的证据。
下一步应补含MDMG变化的定向用例，并测分支数与完整耗时，不能先声称加速比例。

### 2. 青魔仍被整段GCD入口直接排除（验证范围遗留）

`src/optimizer.ts:1537` 保留 `job !== 'BLU'`，与已删除坦克条件同属 `2a55d3c` 引入的职业入口限制。
青魔确实有INT参与武器伤害、模仿状态等特殊公式；这解释了部分可分离预算上界不能直接套用，
并不自动证明整个GCD区间搜索不可用。

用 `/tmp/audit-blu.cjs` 以内存模块加载方式，临时仅去掉入口的BLU排除，
在现有整条区间流程测试中新增种子3、7、11及高/低/不限暴击，并断言BLU实际进入后端。
12项原生测试通过，包含900组既有独立穷举对照。
此实验没有修改仓库运行代码，不含真实大规模青魔性能测试，不能据此直接移除全部青魔保护条件。

### 3. 无坚韧普通职业的固定技速查询关闭相关切线上界（静态性能策略待复核）

`src/optimizerSearch.c:255` 的 `(!context[56] || context[57])`：
无有效TEN维度时，仅整段GCD查询启用该上界，固定技速查询关闭；坦克固定技速查询可以启用。
这是分流遗留，不能单凭代码断言数学必要，也不能因不对称就全局打开。
过去已有上界计算开销超过收益的实验。应在统一后的路径上分别测固定技速查询和整段查询，
再用成本/能力条件表达，而非长期依赖隐含职业代理。

### 4. 食物候选只有最高品级，未证明覆盖全部可行最优食物（候选范围风险）

`src/optimizerInput.ts:200–204` 先过滤 `best===true`、非PIE食物，再只保留最高品级。
手动锁定可以指定其他非PIE食物，但默认自动搜索仍是子集。
没有在这段逻辑中找到逐食物支配性证明；不应直接称默认结果是全体食物的最优。

精确GCD约束下，食物副属性更高不保证支配旧食物。独立算例（不是已复现的真实装备配置）：
70级sub364/div900、原始技速390，无食物GCD2.49；10%速度食物封顶20后技速410/GCD2.48；
封顶40后技速429/GCD2.47。若目标2.48，旧食物可能满足而新食物不满足。
因此“品级更高”不是删除所有旧食物的充分数学依据。还需用实际食物、装备配置找反例或证明当前数据集的候选覆盖。
PIE食物过滤是另一项明确的范围策略，当前还拒绝锁定PIE食物；应明确其目标依据，不能与性能分流混为一谈。

### 5. 坚韧新上界只在WASM收紧，JS回退仍使用较弱版本（实现覆盖不一致）

`src/optimizer.ts:1623` 的 `createSecondaryBudgetBound` 与 `src/optimizerWasm.ts:118–128`
重复维护无TEN/预算适用性条件；最近新增的最低TEN预算下界及折算相关切线在C中，JS没有对应收紧。
这不表示JS结果错误：较松上界通常增加工作量，但不排除真实解。
不过需要共享或测试约束模型，防止只修一个后端，并明确回退性能差异。

## 有明确理由的分流

| 条件 | 当前依据 |
|---|---|
| 低暴击按精确CRT分桶，高暴击可用普通支配 | CRT更高可能违反上限；直接统一普通Pareto会丢失可行解 |
| `feasibleDamageBound`检查高暴击、树搜索另查低暴击 | 上限要求节点最小CRT，下限要求节点最大CRT，不能用同一方向的极值 |
| `betterSpeedIntervalSeed`只对暴击偏好额外比较贪心解 | 无偏好路径已经以同一个贪心解开局，重复运行没有新候选 |
| WASM最多16个根，适配器最多15个选项组加前缀 | ABI容量一致，超限须回退，不是职业限制 |
| 小集合不用原生Pareto、较小任务不用昂贵预热/相关界 | 控制初始化、传输及上界开销；阈值仍需基准校准，但并非算法适用性证明 |
| 非正参考因子、负属性/不支持的食物模型关闭部分对数上界 | 保护上界证明的前提；需要扩展证明与测试后才能放开 |
| 高低暴击、最低减伤和折算目标采用不同约束参数 | 用户要求不同，统一的是求解框架，不是忽略约束差异 |
| 显式`engine=wasm`不预热、自动/wasm-warm预热 | 基准消融开关；正常用户路径不按职业关闭预热 |

额外发现：`filterRemovableSpeedMeldOptions`（`src/optimizer.ts:509`）对高/低暴击都保守跳过仅CRT/速度魔晶石的替换剪枝。
注释给出的反例只涉及低暴击；高暴击是否可安全放开值得定向证明和对照，暂未作为已确认缺陷。

## 建议顺序

先修复魔法武器轴遗漏；再验证青魔整段路径与固定技速相关上界；另行审查食物候选完整性。
JS/WASM约束模型的一致性应列入回归。不能把这些项目合并为“去掉所有if”，也不能把尚未验证的范围长期当职业规则。
