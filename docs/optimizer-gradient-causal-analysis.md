# 梯度方案的耗时归因（2026-10-28）

本文记录取消坦克限制前的实验；后续统一路径和约束修正见[坦克区间搜索报告](optimizer-tank-interval.md)。

战士同步375、范围350–375、GCD2.48 的退步，主要来自反复计算梯度上界的成本。
这次有函数边界直接计时支持；先前“子树上界变松”只是解释额外分支的候选机制，不能当作本例翻倍的已证实主因。

## 方法和单位

先检查未计时版本的完整184个分片诊断，再做两个配置的原版/梯度版计时对照。
在 `refine_plane` 的有效入口及出口调用 `Date.now`，逐原生查询记录梯度耗时、次数、分支数和是否整段GCD搜索。
两个版本使用相同JS查询日志；原版WASM不调用梯度函数，计时为零。
实验补丁见 [gradient-profiling.patch](experiments/gradient-profiling.patch)。

以下累计时间是各 Worker 内的墙钟耗时之和，**不是CPU时间，也不是用户等待时间**。
用户等待还取决于规划、最长 Worker 的工作量和调度。
计时精度为1毫秒，区间计时包含进程被抢占的时间；不声称是指令级CPU分析。

所有查询日志按规划阶段和求解阶段分开核对，查询数、分支总数与Worker诊断完全一致。
计时版两例的分支数和最优伤害均与未计时版相同。
计时版仍通过12项原生内核测试，其中包括900组独立穷举对照。

## 战士：直接测得计算上界的开销

未计时版用户等待为81.14秒 → 159.07秒。
184个分片的累计候选去重时间为58.88秒 → 58.40秒，其他处理216.98秒 → 215.67秒；
累计WASM查询时间却从34.03秒增加到347.44秒。
分片数量相同，各Worker负载也相当均衡。这首先把问题定位到WASM查询内部。

采用同一日志方式补跑后：

| 指标 | 原版 | 全局梯度 |
|---|---:|---:|
| 页面完整耗时 | 88.265秒 | 169.376秒 |
| 分片数 | 184 | 184 |
| 查询分支数 | 20,351,629 | 25,157,032 |
| 累计WASM查询耗时 | 36.778秒 | 370.947秒 |
| 其中梯度细化函数耗时 | 0 | 332.506秒 |
| 除梯度函数外的WASM查询耗时 | 36.778秒 | 38.441秒 |
| 梯度细化次数 | 0 | 52,916 |

分支增加约23.6%，WASM查询耗时却达到约10.1倍。
累计WASM新增334.169秒，其中直接测得梯度函数332.506秒，占新增量约99.5%。
其余查询耗时只增加1.663秒；该部分还包含打包、缓存、调用和日志开销，不能全部归为额外分支。
因此，本例退步的主要原因是梯度计算本身，不是候选去重或额外分支数量。

该原型每次细化最多做16轮，每轮扫描实际候选支持点、更新切线及线性约束项，并进行方向导数二分。
不同梯度权重需要新的支持函数缓存代际。这些工作在许多查询和CRT区间中重复发生。
本例4920次求解查询全部为固定技速查询，没有整段GCD约束乘子可以优化；
但仍做了52,916次细化，成本没有被足够的剪枝收益抵消。
这不等于证明固定技速查询永远不能获益。

代码还在初始根节点上界检查前调用细化，没有先检查原上界是否已经足以剪枝。
尚未对“本可避免的细化次数”直接计数，不能把全部52,916次都声称为无用。

## 龙骑：计算成本被搜索收益抵消，且最长Worker缩短

同步605、580–605、GCD2.46 的计时版结果：

| 指标 | 原版 | 全局梯度 |
|---|---:|---:|
| 页面完整耗时 | 8.190秒 | 5.056秒 |
| 分片数 | 4 | 4 |
| 查询分支数 | 16,407,544 | 1,372,414 |
| 累计WASM查询耗时 | 5.738秒 | 5.733秒 |
| 其中梯度细化耗时 | 0 | 4.185秒 |
| 除梯度函数外的查询耗时 | 5.738秒 | 1.548秒 |

这里新增的梯度成本约4.185秒，基本被其余查询耗时减少4.190秒抵消。
页面仍明显加速，是因为原来的工作量集中在一个慢Worker上，优化后负载更均衡。
详细Worker负载保存在原始结果中。不能用“四个Worker的总时间”单独预测页面耗时。

## 证据范围与后续策略

两个配置各版本各补跑一次，没有足够独立重复来给出置信区间或总体分位数。
计时版本相对未计时版本有约6–9%的战士耗时差异，混合了计时/日志扰动与系统波动，不能单独解释为计时器成本。
两次战士对照都显示明显退步，且函数边界计时远大于剩余查询开销，支持主因判断。
这些证据不能证明所有退步案例都由相同原因造成。

因此不宜仅按“职业”“目标GCD更短”或原始装备数量决定启用。
应区分整段GCD搜索和固定技速查询，并衡量梯度成本是否被搜索收益抵消。
目前试验中的500万分支按需策略，只是一个已测试的成本保护方案，不是已求得的最优门槛。
它是否值得采用，还要同时列出长任务节省的绝对时间、最坏额外等待及没能保留的收益。

下一步可分别做消融实验：先用原根上界排除已可剪枝的区间、限制梯度扫描预算、对整段GCD与固定技速查询使用不同门槛。
“同时保留两个上界、逐子树取较小值”也可研究，但它只能防止上界更松，不能消除计算新上界的成本，仍需计时。
这些改动尚未在本次归因实验实施，不计入收益。

## 坚韧与坦克搜索路径的关系

战士案例的目标是 `minimumTenacity`、最低减伤0，没有额外的最低减伤约束或减伤折算；
普通坚韧伤害因子仍参与伤害计算。
因此不能将这次退步直接归为减伤折算公式的成本。

| 指标 | 战士375/GCD2.48 | 龙骑605/GCD2.46 |
|---|---:|---:|
| 分片数 | 184 | 4 |
| 求解阶段原生查询数 | 4920 | 44 |
| 梯度细化次数 | 52916 | 112 |
| 每次细化平均累计计时 | 6.28毫秒 | 37.37毫秒 |
| 梯度细化累计时间 | 332.506秒 | 4.185秒 |

战士单次细化在这两个样本中更便宜，调用次数却约为龙骑的472倍。
两个样本的候选结构不同，此比较不能作为“同一查询添加坚韧维度”的受控消融，
但足以说明不能把战士的累计耗时解释成其单次细化特别慢。

`canSearchSpeedInterval` 当前显式排除 `damage.mainStat === 'VIT'`，即坦克。
战士走固定技速分片查询；每个独立查询又按CRT区间做细化，当前实现不跨查询复用这些梯度计算。
查询日志确认战士全部4920个求解查询均非整段GCD搜索；龙骑44个均为整段GCD查询。
所以当前代码中的坦克分流与重复计算存在直接结构联系，这不是“坚韧在数学上必须如此”的结论。

坚韧额外维度还可能改变候选前沿和剪枝效率，尚未做同一输入的专项消融，无法量化其贡献。
优先验证的应是减少重复细化、先做便宜的剪枝，以及在保留坚韧条件正确性的前提下测试坦克整段GCD路径，
而不是未经计时就简化坚韧公式。后者及整段GCD路径尚未在本节实现。
